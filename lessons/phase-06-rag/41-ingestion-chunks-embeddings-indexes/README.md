## Why this matters

A retrieval system cannot cite, filter, update, or roll back evidence that it
cannot identify. Many RAG demonstrations begin with “split these strings and
put them in a vector database.” A production knowledge pipeline needs a much
stricter answer to every one of these questions:

- Which source record produced this chunk?
- Which document version was active?
- Was the content normalized before offsets were calculated?
- Which license allowed the content to enter the index?
- Which tenants may retrieve it?
- Which chunking and embedding configuration produced the index?
- Can the exact build be reproduced and compared with its predecessor?

This lesson builds that foundation without hiding it behind a framework. The
corpus is synthetic and public-safe. The index uses a transparent,
deterministic hashing embedding implemented with the Python standard library.
It is not a semantic model and it is not presented as one. Its value is that
you can inspect every feature, vector, score, identity, and failure. An
optional script shows where a pinned Sentence Transformers model fits after
the contract works.

The output becomes the shared evidence layer for lessons 42–44. Lesson 40 said
that RAG is useful when knowledge must be fresh, filtered, and cited. This
lesson makes those properties concrete: versioned source records, pre-ranking
tenant metadata, exact source offsets, content hashes, and a build manifest.

## Learning outcomes

By the end, you can:

- define a source schema with version, provenance, license, and entitlement
  metadata;
- explain why ingestion must fail closed instead of quietly skipping a bad
  record;
- normalize Unicode and whitespace while naming the offset coordinate system;
- create section- and sentence-aware chunks with sentence overlap;
- derive stable chunk IDs from document identity, version, source span, and
  content;
- recover the exact chunk text from its normalized source section;
- implement and inspect a signed feature-hashing embedding;
- explain cosine similarity, dot product, and Euclidean distance;
- prove why those three metrics have equivalent rankings for L2-normalized
  vectors;
- compare exhaustive scoring with an approximate candidate generator;
- measure approximate recall against exact results instead of assuming it;
- distinguish a transparent CPU teaching baseline from a learned production
  embedding model;
- create a manifest that binds source, configuration, documents, chunks, and
  vectors by SHA-256.

## Under the hood

### Source identity and idempotence

A document identity is `(document_id, version)`. The ingestion program rejects
the same pair twice. It also requires a numeric semantic-version shape, a
non-empty tenant list, unique section IDs, and a license in the configured
allowlist.

Idempotence means the same source bytes and configuration produce the same
normalized records, chunk IDs, vectors, and manifest. It does not mean every
future implementation must preserve IDs. Changing normalization, chunk size,
overlap, or embedding features is a new index build and should create a new
manifest. A real platform normally gives that build its own immutable index
version.

The source-record hash covers the canonical JSON record before ingestion-only
fields are added. Each chunk also has a text hash. Hashes detect accidental
change and bind lineage; they do not establish that a source is true or safe.

### Normalization and offsets

`normalize_text` applies Unicode NFKC, normalizes line endings, collapses
horizontal whitespace, and trims the result. These operations may change
string length. Therefore, `start_char` and `end_char` are explicitly declared
to use `normalized_section_text`, not the original byte stream.

For a chunk `c`, verification performs:

```text
section.text[c.start_char:c.end_char] == c.text
sha256(c.text) == c.text_sha256
```

If legal or audit requirements demand original byte offsets, preserve the
original object and an offset mapping rather than pretending normalized
character positions are original byte positions.

### Section- and sentence-aware chunks

The chunker never crosses a section boundary. It collects whole sentences
until the target word count is reached and carries one sentence into the next
chunk. Overlap can preserve a local reference such as “this procedure,” but it
also duplicates evidence. Later context assembly must deduplicate overlapping
claims.

There is no universal chunk size. Small chunks can improve localization but
lose surrounding explanation. Large chunks preserve context but consume
prompt space and can dilute ranking. The unit should follow the source
structure and the questions users ask. Record the configuration and test
changes against fixed qrels rather than choosing a fashionable number.

The stable ID is:

```text
"chk_" + first_24_hex(
  sha256(document_id, version, section_id, start, end, text)
)
```

Including the version prevents a revised source from masquerading as its old
evidence. Including the span and text makes boundary changes visible.

### The transparent embedding

The baseline extracts lower-case word features and character trigrams. Each
feature is hashed to one of 96 buckets and receives a deterministic positive
or negative sign. Signed hashing reduces systematic collision bias, but
collisions still exist. The vector is then divided by its L2 norm.

This embedding can match shared words and some morphological fragments. It
does not learn that “credential” and “token” are semantically related unless
their visible features overlap. That limitation is intentional: a weak,
inspectable baseline exposes what a learned bi-encoder contributes.

The optional configuration pins a model ID and repository revision and
disables remote code. Running it still introduces downloaded model files,
dependency resolution, license review, and supply-chain ownership. Treat the
checked-in revision as course configuration that must be revalidated in your
organization, not as universal approval.

### Cosine, dot product, and L2

For vectors `q` and `x`:

```text
dot(q, x)    = Σ q_i x_i
cosine(q, x) = dot(q, x) / (||q||₂ ||x||₂)
L2(q, x)     = sqrt(Σ(q_i - x_i)²)
```

When both vectors have norm one:

```text
cosine(q, x) = dot(q, x)
||q - x||²   = 2 - 2 dot(q, x)
```

Higher cosine and dot scores therefore correspond to lower Euclidean distance.
The verifier confirms equivalent rankings and the numeric identity. If you
forget normalization, dot product also rewards vector magnitude and the
rankings may differ.

### Exact versus approximate retrieval

Exact search filters authorized chunks and scores every remaining vector. Its
work grows approximately with `authorized_chunks × dimensions`.

The teaching ANN path computes five deterministic random-hyperplane bits for
each vector. A query considers only vectors whose signature differs by at most
one bit, then applies the same exact cosine score inside that candidate set:

```text
all authorized vectors -> LSH signature filter -> candidates -> exact top-k
```

This is an honest candidate experiment, not a claim that the toy LSH is a good
index. It can return fewer than `k` results and lose relevant chunks. The
report records candidate count and recall against exact top three. On such a
tiny corpus, timing is dominated by Python and clock noise; do not use its
nanosecond values to choose infrastructure. The transferable method is to
measure recall and latency together on a representative corpus.

## Cost and safety

The standard path uses a tiny synthetic corpus, local CPU, and negligible
disk. No cloud resource is created.

Corpus ingestion is a security boundary. A file being readable does not grant
permission to index it. Validate source ownership, license, retention,
classification, tenant entitlements, and deletion procedures before
processing real data. Do not put credentials or personal data in the course
fixtures.

Metadata filtering later must occur before ranking and prompt assembly. Tenant
labels in a chunk are useful only if a trusted caller identity is mapped to
them. A caller-supplied `tenant_id` is suitable for this local lab, not
authentication.

An embedding can leak information through nearest-neighbor behavior and is
derived data subject to retention controls. Model downloads add license and
supply-chain obligations. Use an isolated cache, pin revisions, verify
artifacts, and delete the cache when no longer needed.

### 2. Follow one source span

```bash

import json
from pathlib import Path

root = Path("artifacts/index-a")
docs = [json.loads(x) for x in (root / "documents.jsonl").read_text().splitlines()]
chunks = [json.loads(x) for x in (root / "chunks.jsonl").read_text().splitlines()]
chunk = next(x for x in chunks if x["document_id"] == "alpha-access-policy")
doc = next(x for x in docs if x["document_id"] == chunk["document_id"])
section = next(x for x in doc["sections"] if x["section_id"] == chunk["section_id"])

print("equals stored text:", recovered == chunk["text"])
PY
```

The last line must be `True`.

## Troubleshooting

`ModuleNotFoundError` from `vector_search.py` usually means it was invoked from
another directory with a modified module path; use the documented command from
the lesson directory.

If the exact relevant hit fails, inspect token features and collision effects.
Do not simply widen `top_k` until the test passes: identify whether the source,
chunk boundary, query, embedding, or metric caused the miss.

If IDs differ between builds, compare source/config hashes first. Then inspect
JSON serialization order, Unicode normalization, and accidental timestamps.
Build metadata that changes every run should live outside identity-bearing
content.

If approximate candidates are empty, that is a valid observation for this
index. Increase the Hamming radius as an experiment and measure the candidate
and recall change. Do not silently fall back to all vectors because that hides
the ANN failure.
